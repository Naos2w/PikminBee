# PikminBee Wi-Fi browser controller (v0.4 source prototype)

This is a **private LAN-only, opt-in** controller. It shares the same Android GPS foreground service as the phone UI and floating bee controls. It does not install or operate a second mock-location engine.

## Phone + MSI user flow

1. On the phone, connect to a trusted private Wi-Fi network.
2. Start a PikminBee mock-location session through the phone, with the explicit Android developer-option permission already granted.
3. Open the phone's **Wi-Fi 遠端控制** section and tap **開啟網頁控制**.
4. The phone shows a private network URL like `http://192.168.1.50:8765/` and a fresh six-digit pairing PIN.
5. On MSI or another device **on the same Wi-Fi**, open the URL; enter the PIN.
6. **Return to the phone and tap 核准裝置**; pairing does **not** create a remote control session before this step. The optional last-real-location sharing checkbox starts unchecked in both Android and floating approvals, including every renewal. Sharing requires an affirmative selection for that specific request; previous consent is not carried over.
7. From the browser, click OpenFreeMap to choose coordinates, teleport, select ordered stops, start a pedestrian route, pause, resume, stop or restore real GPS. Browser map style supports **Auto/Liberty/Bright/Positron/Dark** without a Google Maps API Key.
8. Tap **關閉並撤銷配對** on the phone to disable the listener, revoke sessions and rotate pairing on the next start.

**All operations require user intent.** Wi-Fi control is off by default; stopping the GPS foreground service also stops the Wi-Fi listener. When the bound Wi-Fi IPv4 address disappears/changes, the listener automatically shuts down. It never binds to `0.0.0.0`, a public address, or a mobile network.

## API and control semantics

- `GET /` / `GET /controller.js`: locally served controller UI.
- `POST /api/pair`: six-digit PIN + browser device name; returns short-lived pending ticket only.
- `GET /api/pair/status` with `X-PikminBee-Pending`: polling while the phone decides. An approved browser receives a **two-hour, non-sliding** bearer session. Frequent state polls never silently extend it.
- All control calls require the in-memory `X-PikminBee-Token` header.
- `GET /api/state`: current simulated position, mode, moving/paused/parked state, route draft and decimated active route, plus the session time remaining. Browser polls every two seconds while visible (no WebSocket). When the tab becomes visible, it refreshes immediately; brief fetch failures retry without granting fresh credentials.
- **Explicit session renewal:** The browser displays a countdown and an optional **「從手機核准延長 2 小時」** action. `POST /api/session/renew` creates a 90-second pending approval **only while the existing peer-bound token is valid**. The phone Settings panel shows the renewal request; the owner must explicitly approve or deny it. The same browser polls `POST /api/session/renew/status` using the old token and pending ticket. On approval the server **rotates** to a fresh two-hour token, revokes the prior token and revokes separate precise-real-GPS sharing consent. Denial, expiry, restart, IP mismatch and Wi-Fi changes never renew or restore authority. No cookies, localStorage, background renewal or periodic rolling refresh are used.
- `POST /api/teleport`, `/api/points/add`, `/api/points/undo`, `/api/points/clear`, `/api/route/start`, `/api/speed`, `/api/speed/default`, `/api/control`: shared existing location-service operations. Speed presets in all control surfaces use km/h (Slow 0.8, Walk 1.4 factory default, Fast 10.8). The remote `/api/speed` changes the **current session** and may update an active walk without restarting its route; authenticated `/api/speed/default` explicitly saves the selected **personal startup default**. Older `walk_speed_preset` settings are migrated on first launch. Only the personal default survives a fresh process launch.
- `stop` keeps the simulated GPS where it is. `restore-real` explicitly ends mock mode **and closes the web listener**.
- Routing uses Valhalla pedestrian roads. Failed route planning returns an error state; it never silently switches to a straight-line walking path.
- Server, **not just browser buttons**, checks route limits: normal route 15 stops, looping normal route 14 stops. Dedicated flower mode and all `/api/flowers/*` handlers are retired (HTTP 410); `mode=FLOWERS` cannot create, preview or start a route. Historical flower-labelled favourites may be loaded as **ordinary route drafts** without deleting the original saved record. Invalid route requests return HTTP 400/409 without changing the draft; a failed external route response does not move GPS.
- The browser disables Add/Start when preconditions are missing, and shows the ordinary-route limit. These controls are hints only; direct API requests are independently validated.
- **UI/UX fix branch (2026-11-24):** A fixed compact Pause/Resume/Stop control is always available while walking on mobile (all sheet states), portrait/landscape tablets (including a closed drawer), and desktop; Stop requires explicit confirmation. Native Android route Stop also requires confirmation in the main map and route sheet. Ordinary non-loop routes now allow 15 waypoints in both Android and Web, while 14 remain the maximum for loop-return routes. Dark OpenFreeMap road colours are slightly brightened in both native and Web styles. These changes are **source-only until device/browser UAT**.

## Safety and limitations

- This version uses **plain HTTP on a private Wi-Fi IP**. Authentication cannot prevent a malicious actor capable of intercepting local traffic from reading network packets. **Do not use on shared/public/untrusted Wi-Fi**, do not expose port 8765 to the internet, and do not enable router port forwarding.
- Credentials and session tokens are memory-only. They are not written to URLs, cookies, cloud accounts or device storage. Browser refresh requires new phone approval. Renewing requires another explicit phone approval and only works before the old session expires.
- Bad PIN entries are throttled; five failed entries lock that peer for five minutes. All API requests are rate-limited. Session tokens expire after two hours regardless of request volume and bind to the approved peer IP. Pairing revokes prior sessions only after a new phone approval; renewal also rotates the approved token. In this unencrypted HTTP design, an extended session increases the risk of exposure, so only trusted private Wi-Fi is supported.
- A bounded HTTP server accepts only private IP clients and validates the `Host`, `Origin`, request method, headers and JSON body length. Cross-origin browser control is not enabled.
- #172 shutdown privacy hardening: the server owns accepted client sockets before queueing them and closes both queued and active connections during listener shutdown. A late accepted socket is closed instead of queued; workers check listener state before dispatch and before returning a response. Closing a socket cannot retract bytes already delivered or guarantee cancellation of a handler already running. Session authorization and application-level cancellation remain separate requirements. Local socket lifecycle regression tests use only unconnected sockets and loopback; actual device/network revocation testing remains required.
- Commercial threat assessment (#172): the PIN, pending ticket, bearer token, coordinates and responses still travel over plaintext HTTP. Host/origin validation, private address binding, IP-bound sessions and no-store headers do not authenticate the transport or protect against an on-path peer. The browser may also contact the external map-tile provider. This source fix is not an encrypted or mutually authenticated transport, is not approval for public distribution, and does not resolve in-flight application work or previously received data. Keep the commercial release gate closed until an independently verified transport and explicit owner decision, or remove the LAN functionality from the product rather than hiding it.
- Browser map: **OpenFreeMap Auto/Liberty/Bright/Positron/Dark**, using a locally bundled, hash-verified copy of **MapLibre GL JS 6.18.0** (BSD-3-Clause; see [THIRD-PARTY.md](THIRD-PARTY.md)). Browser JavaScript/CSS is served from the phone, with a CSP disallowing third-party executable scripts. The map still needs internet access to fetch OpenFreeMap vector tiles/style assets. If map tiles cannot load, latitude/longitude input and remote controls remain available.
- Browser style preference is **local to that browser** (no phone style mutation); the phone offers the same four named keyless map styles and an automatic appearance mode. Switching map styles does **not** trigger teleport or GPS route commands.
- Mobile app map remains OpenFreeMap or official Google Maps SDK. The browser does not include Google Maps JS, which would need a separately authorised web API key/billing.
- Android targetSdk 36: current `INTERNET` permission covers LAN access. **Before updating targetSdk to 37**, add the Android 17 `ACCESS_LOCAL_NETWORK` runtime permission flow.
- Browser pairing, phone approval, the two-hour countdown/renewal controls, map rendering, LAN switching, HTTP errors and HyperOS background operation are **not device-tested yet**. Source/JVM tests alone do not qualify this as released. Grouped POCO UAT must include browser style switching, 15-stop ordinary route and 14-stop looping limits, legacy favourite conversion, retired-mode/API rejection, renewed-token rotation/revocation, disconnection, and phone/web draft synchronisation.
- For internet/public-network access in the future, design a genuinely encrypted and mutually authenticated transport, not this private-LAN HTTP endpoint.

## Validation approach without APK churn

Every edit: compile Kotlin only where useful. Before PR review: `./gradlew :app:testDebugUnitTest :app:lintDebug --offline`. Only after a coherent UAT milestone: manual `assembleDebug`. Keep the GitHub PR in Draft until ready for review; this avoids unnecessary Actions Android runner minutes.
