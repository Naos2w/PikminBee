## 2. P0 — existing-source gap audit (no new mode)

- [x] **S1 · Daily steps / Health Connect source reliability (fixed):** audited `FloatingControls.kt` and found a reproducible date-only Health Connect cache defect: a time-zone change without a date change could reuse an aggregate computed from the wrong midnight boundary; reopening the overlay could briefly display old permission-dependent data. Added `FloatingDailyStepsCache` keyed by **local date + IANA time zone**, monotonic 60-second freshness, 15-second bounded retry on unavailable/denied reads, forced revalidation on overlay reopen, cancellation/invalidation on close/rollover, and per-request tokens to reject stale in-flight completions. Pure Kotlin regression tests cover **same-date zone change, midnight, revocation/failure, real zero, stale expiry, concurrent reads, elapsed-clock rollback and 5-second UI tick throttling**. The HC total, local-sensor count and virtual estimate remain separate. **265 JVM tests (0 failures), local Android Lint and PR CI tracked separately**; this source fix is not proof of real POCO/HC acceptance.
- [x] **S2 · Route/speed/step source consistency (fixed 2026-11-23):** identified two source defects in `MockLocationService.tick`: (1) reducing an existing looping route to modulo distance **before** detecting speed-leg crossings dropped segment changes when one Android tick crossed several laps; (2) non-loop progress added the **requested** distance instead of the accepted distance, allowing internal progress beyond the terminal route length. Added the pure, testable `RouteTickProgression` used by the service for canonical accepted travel and bounded elapsed time; replaced the duplicate modulo-only speed controller with the existing `WalkSpeedPlayback`, which samples all crossed stops and full laps, reuses current range speed on an identical selection and samples anew for a new route. All virtual step updates still use only accepted route metres; GPS jitter is test-provider-only, and pause/stop/park never generate new travel. Added **11 JVM regression tests** for 0.8/1.4/10.8 presets, custom speed during pause/resume, non-loop terminal clamp, 6 complete laps within one tick, repeated range selection, idle/stop time, jitter-only reports and invalid input. **MSI 276 JVM tests (0 failures/skips) and Android Lint exit 0**; GitHub PR/CI is the next gate. Real POCO App/overlay/Wi-Fi and Health Connect acceptance remains under U1–U3; do not claim device verification.
- [x] **S3 · Virtual step-sync source integrity (fixed 2026-11-23):** audited `EstimatedStepLedger`, `HealthConnectStepSync`, foreground Settings and `EstimatedStepsSyncWorker`. Before this change the manual and background writer could race, disabling consent or discarding a queue during a batch did not stop stale subsequent writes, a 50-item slice could leave 251–500 records stranded after bounded worker retries, a single malformed JSON item could erase the decoded queue, and `todayOwnVirtualSteps()` counted entire cross-midnight records as today's manual estimates. Introduced one in-process sync mutex, a testable consent/pending recheck **per session**, stable `pikminbee-virtual-<session ID>` client-record retries after local ack failure, full ledger drain in bounded 50-item chunks (up to the existing 500-item cap), safe item-by-item legacy decode, and time-proportional **estimated** overlap for cross-midnight own-record counts. User-facing details explicitly identify this day attribution as an estimate, not sensor data. **Still opt-in, with `Metadata.manualEntry`; no new daily cap, Health Connect permissions or third-party sensor spoofing.** Regression tests cover opt-out, discard, permission/write failure, ack retries, coroutine cancellation, 120-/500-item queues and midnight overlap. **MSI 294 JVM tests (0 failures/skips); Android Lint and GitHub PR CI tracked separately**. Actual POCO permissions, Health Connect accepted records and date rollover remain U3 UAT, not claimed passed.

## 3. P1 — existing flower-image recognition, not an invented new route mode

- [x] **Prototype exists:** `BloomDetector` supports colour/pale candidates from static, user-selected images; `BloomCaptureService` supports explicit Android MediaProjection consent with no capture-protection bypass. Manual image-pixel → GPS anchor preview and optional *unverified*, user-confirmed local flower-catalogue bridge already exist (PRs #10–#12, #90). Sources: [FLOWER-VISION.md](FLOWER-VISION.md), [Issue #17](https://github.com/Naos2w/PikminBee/issues/17).
- [ ] **F1 · Honest recognition accuracy:** assemble only user-authorised, non-protected, non-sensitive labelled example frames and negatives; record precision, recall, per-class false positives/negatives across map scales and image sizes. Until those exist, do **not** claim real-game recognition quality or tune to imaginary examples.
- [ ] **F2 · Independent coordinate validity:** compare pixel-to-GPS calibration against independently verified landmarks. Leave-one-out RMSE between self-supplied anchors alone is **not** ground-truth flower-position accuracy. Do not auto-inject unverified detections into GPS routes.
- [ ] **F3 · Safe capture/session behaviour:** verify new consent per MediaProjection session, resize/orientation, protected black frames, stop/cancel and screen-share permissions. Keep image pixels/tokens transient; never bypass FLAG_SECURE. Add source tests where possible and retain POCO cases under #17.
- [ ] **F4 · Evidence-driven enhancements only:** after F1/F2 evidence, decide which false-positive filters, UX hints or manual confirmation improvements genuinely need code; use small focused feature PRs rather than duplicating the detector.
