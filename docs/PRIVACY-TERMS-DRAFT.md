## Versioned consent contract

- Terms and privacy revisions are distinct identifiers tied to the exact approved texts; no default acceptance, no upgrade of the legacy `setup_completed` flag into a receipt.
- An explicit confirmation stores the exact pair and a positive local acceptance timestamp together, atomically; persistence failure must not unlock functionality. On restart, only a valid exact matching receipt is accepted; a missing, corrupt or mismatched record requires review.
- Refusal does not create a receipt or request permissions; user may leave. Do not delete existing saved data. Withdrawal and major changes must require fresh confirmation before further covered functionality; a previously stored receipt must not be reused after withdrawal.
- Local review and rejection must work offline; no server call or account is required to check the receipt. Store only receipt versions and timestamp, not location, device ID or a new analytics identifier.
- Source foundation: `LegalConsentPolicy` and `LegalConsentReceiptCodec` define the exact revision check and a single JSON record (schema 1, terms, privacy, acceptedAtMillis). Missing or malformed records, unsupported schema, invalid types, invalid timestamp and stale document revisions require review. `LegalConsentStore` uses a single process-wide owner and an isolated `noBackupFilesDir/legal-consent.json` record, with a size limit, synced temporary file, atomic replacement and read-back before reporting acceptance. A successful withdrawal replaces the receipt with a non-receipt marker; if replacement or its verification fails, the store attempts to remove only the consent record and verify its absence. Unrelated data is untouched. Failed reads/writes keep this process blocked, and unsuccessful withdrawal must be surfaced and retried, not reported as complete. If both replacement and removal fail and the process dies before a successful retry, an older receipt may remain on disk. No local storage design can guarantee persistence when all writes and deletions are unavailable; the live flow must stop covered operations immediately, show a blocking retry state on unverified withdrawal, and must not claim success. On-device filesystem, power-loss, backup and service-stop behavior still require acceptance testing before wiring any live entry-point gate. No approved document revision or default consent is embedded.
- Terms/privacy acceptance is not permission consent, LAN location-sharing consent or advertising consent. No new permission, sharing grant or network traffic is triggered by the receipt alone.
- Integrate into the existing #144 first-use flow only after owner review, before any sensitive feature or external network initialisation requiring the disclosure. Audit all entry points (including service restoration / LAN) rather than gating only the main Compose page.
- Storage distinguishes absence from oversized, unreadable or malformed UTF-8 files. Only a confirmed absent record can establish the removal fallback; invalid content is a review-required error, not proof of removal. This does not guarantee recovery from complete storage failure.
