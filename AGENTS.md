# PikminBee repository development instructions

- Read [docs/COMMERCIAL-READINESS.md](docs/COMMERCIAL-READINESS.md), [docs/BRANCHING.md](docs/BRANCHING.md), and [docs/TODO.md](docs/TODO.md) before work. [Epic #168](https://github.com/Naos2w/PikminBee/issues/168) and the linked Issues are authoritative for gate status, latest decisions and acceptance evidence; do not create a parallel task list.
- Personal repository only: verify Naos2w Git author/committer and authenticated personal GitHub account before any write. Use the independent personal Projects connector. Never switch the shared CLI default or use unrelated accounts. Stop on mismatched identity. Keep worktrees isolated; do not rewrite existing history.
- Current phase: commercial feasibility (#169), sensitive-feature/permission cleanup (#171), legal/privacy/onboarding (#170). Resolve the actual product compliance scope before new feature or ad work. Do not build or optimize game-cheating, anti-detection, fabricated health activity or policy-evasion functions; remove non-compliant behavior rather than hiding it.
- Keep implementation, CI, fixed-signer UAT packaging, actual device acceptance, Play review and AdMob review separate. Do not mark Issues done without their acceptance evidence. Preserve installed data; no unapproved install/uninstall or data deletion.
- Current production hold: no staging-to-main promotion, production tag/release, public production APK/AAB, live ads or paid acquisition until the applicable #168 gates and explicit owner approval. Separately approve production advertising only after public store listing, AdMob verification and readiness review. Never provision or expose credentials, payment settings or legal declarations on behalf of the owner.
- Follow the established branch/PR/CI rules. No auto-version bump, auto-packaging or auto-release on routine commits. Use local tests first; record source SHA, actual results and limitations. Maintain the map-first UI and review new visual directions in the corresponding Issue.
