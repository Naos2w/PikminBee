# PikminBee repository development instructions

- Read [docs/BRANCHING.md](docs/BRANCHING.md) and [docs/TODO.md](docs/TODO.md) before work. Existing GitHub Issues and Projects are authoritative for requirements, owner decisions and acceptance evidence; do not create a parallel task list.
- Personal repository only: verify Naos2w Git author/committer and authenticated personal GitHub account before any write. Use the independent personal Projects connector. Never switch the shared CLI default or use unrelated accounts. Stop on mismatched identity. Keep worktrees isolated; do not rewrite existing history.
- Current direction (owner decision 2026-11-27): personal development and device UAT only. Prior store publication, advertising, monetisation, branding migration and commercial-only work are discontinued. Retain ordinary Android permissions, source transparency, privacy/security protections, third-party licences and data integrity. Do not build or optimise game-cheating, anti-detection or policy-evasion functions; do not mislabel estimates as hardware sensor measurements.
- Preserve the approved existing-feature baseline. Before removing or materially restricting an existing function, document the exact affected actions, rationale, replacement and acceptance impact in the canonical Issue and obtain owner confirmation; do not silently remove unrelated functions in a UAT promotion. Owner decision (2026-11-27): retain periodic route-estimate synchronization during route movement with clearly identified estimated/manual provenance, Android-granted WRITE_STEPS permission. Owner clarification (2026-11-27): no separate app-side authorization state, preference or switch for route estimates; keep legacy history separate and never misrepresent estimates as sensor measurements.
- Keep implementation, CI, fixed-signer UAT packaging and actual device acceptance separate. Do not mark Issues done without their acceptance evidence. Preserve installed data; no unapproved install/uninstall or data deletion.
- Keep main reserved; work through develop and separately approved staging UAT. Do not publish public production artifacts or change signing identities, credentials, payments or external accounts without explicit owner authorization.
- Follow the established branch/PR/CI rules. No auto-version bump, auto-packaging or auto-release on routine commits. Use local tests first; record source SHA, actual results and limitations. Maintain the map-first UI and review new visual directions in the corresponding Issue.
